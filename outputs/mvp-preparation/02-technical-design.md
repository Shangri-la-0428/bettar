# P0 技术与数据设计

日期：2026-10-14｜状态：实施准备稿，尚未实现。

本稿承接[战略 v0.2](../ai-bouldering-strategy-v0.2.md)，把首轮方案收敛为可复现的本地研究原型。下述选择是拟议默认方案，不代表用户已逐项认可；其中 P0 范围比战略文档中的长期候选更窄。

## 1. 范围与技术选择

场景为宽 3 m、沿面高 3 m 的简单平面墙，初始垂直，另试 10° 仰角。库存共 16 个独立实例：6 个 `jug`、4 个 `directional_edge`、6 个 `foothold`。形状、尺寸、接触点与人体参数均为合成建模假设，不是实测产品数据。

三个情境为“脚先移动再抬手”“侧拉横移”“脚点重定位”。每段包含 2–4 次手部换点，脚步单独计数；不包含 dyno、脚钩。名称描述设计意图，P0 不验证侧拉受力是否成立。

固定板与自由摆点使用相同表示与评估器：前者锁定安装布局，只选择线路接触点；后者允许在边界内改变安装位置和朝向。先做一个合成固定板参照，再做同库存的自由布局小试；它不冒充真实 MoonBoard／Kilter 配置。

| 模块 | P0 选择与职责 |
|---|---|
| 数据与验证 | JSON、JSON Schema；Python 校验类型、引用、库存、模式锁定与几何约束 |
| 候选与求解 | Python、NumPy、SciPy；模板提出候选，数值 IK 求解离散接触姿态 |
| 几何 | 参数化生成显示模型和保守包围体；Trimesh 按实际需要增加 |
| 查看器 | Vite＋TypeScript＋Three.js；导入结果包、查看、比较、标注和导出 |
| 协作 | 当前 Codex 对话修改请求或候选并调用 CLI；不集成模型 API |

不安装 Blender；P0 无 React、拖拽编辑器、FastAPI、数据库或 API key。以后导入 GLB 时仍沿用同一数据契约，网格不能替代接触属性。

## 2. 数据契约与坐标

各对象均含 `schema_version`、稳定 `id`、修订号及来源。来源区分 `synthetic_assumption`、`observed`、`derived`，保存说明；未经验证的数值不得标为实测。

| 对象 | 必要内容 |
|---|---|
| `scene` | 墙尺寸、倾角、安装区域；岩点定义与独立库存实例；显示几何、安装包围体、局部接触区域及方向 |
| `body_profile` | 骨段长度、关节轴与范围、根姿态定义、来源与假设；所有状态复用同一份 |
| `request` | 场景／人体引用、情境、起终点接触要求、锁定布局、允许修改的变量、候选预算、随机种子、评价配置 |
| `candidate` | 安装布局、所选线路岩点、起终点角色、多个动作方案及设计理由、生成方式 |
| `evaluation` | 输入指纹、逐项状态、残差与证据、求解姿态、求解预算、未检查项、版本与耗时 |
| `review` | 候选和评估指纹、用户意见、定位对象／状态、时间；不改写计算结果 |

岩点定义与实例分开：一个实例只能安装一次，重复使用同一类型须占用另一实例。接触引用 `placement_id + contact_id`，不引用屏幕坐标。线路角色、手脚接触与动作顺序分别存储；按高度排序不构成动作方案。

接触区域先采用局部中心、容许半径及允许肢体类型；候选明确选择区域内的接触目标。方向向量用于可视化与未来求解，不把 `jug` 等类型名直接换算成摩擦系数或抓力。骨架关节点代表简化的手／脚末端，不能解释为已验证的手指抓法或鞋底接触。尺寸、区域与方向更新均需形成新的资产修订。

统一米制右手系：世界 `x` 向右、`y` 向上、`z` 朝攀爬者。墙原点在底边中点；局部 `u` 向右、`v` 沿墙向上、`n` 朝攀爬者。正倾角 α 表示墙顶向攀爬者倾出：

`u=(1,0,0)`；`v=(0,cosα,sinα)`；`n=(0,-sinα,cosα)`。

因此 `u×v=n`，且世界点为 `origin + u·U + v·V + n·N`。墙外沿为 `U∈[-1.5,1.5]、V∈[0,3]`；四边各预留 0.2 m 后，允许安装区域为 `U∈[-1.3,1.3]、V∈[0.2,2.8]`，整个安装投影包围区域都须位于其中。10° 时世界垂直高度为 `3cosα`。岩点安装基准位于 `N=0`，局部正 z 向外；绕 n 的安装角遵循右手规则。JSON 输入角度用度，计算边界统一转弧度。世界变换由墙和安装参数派生，避免两份可编辑坐标不一致。

布局模式示意，仅为契约片段：

```json
{
  "layout_mode": "fixed",
  "layout_locked": true,
  "reference_layout_hash": "sha256:…",
  "placements": [{
    "id": "p01", "inventory_instance_id": "jug_01",
    "wall_uv_m": [0.25, 1.20], "rotation_deg": 30
  }]
}
```

固定模式校验全部安装项与参照一致；改变墙角需新请求及重评。自由模式解锁安装，但不解锁库存、墙边界或验证规则。

## 3. 动作状态与 IK

**候选生成。** 模板先确定接触事件，再枚举有限库存组合。固定板只选接触点与顺序；自由模式采样安装初值，或由已知姿态反推接触目标，再检查能否落实到墙内。随后只在已解锁变量内有限扰动，调用冻结的检查器，保留不同候选并记录淘汰原因。排序只依据已检约束与请求的几何、序列条件；未知项不得充当通过，结果不能解释为难度或趣味评分。全部尝试受请求预算约束，不加入动态学习。

一个动作方案包含有序 `states` 与 `events`。状态存 LH／RH／LF／RF 四肢的接触引用，脱离接触用 `null`。事件记录哪只手脚从何处换到何处，并包含释放与重新接触状态。初始抓点和单纯释放不计作手移动；一次到新接触点的完成换点计一次，脚部事件另计。

P0 必检 `request_conformance`：四肢字段齐全，非空引用存在且允许该肢体类型；方案有初始状态与事件链，不得以空接触状态通过。每次事件只改变指定肢体的接触，其他接触保持，依次匹配前态、释放为 null、接触目标和后态，事件之间首尾一致。手部完成换点须为 2–4 次，并满足请求指定的次数或范围，脚步另计；同点释放再抓不增加换点数。请求必须明确非空的起点／终点接触要求，首尾状态逐项满足，且布局与变量锁定条件未被违反。缺失、跳步、未到目标均为 fail。这些是数据和序列规则，不证明释放过程稳定或动作可完成，对应 03 的请求符合性验收。

P0 使用可移动根节点、固定骨长的简化关节链；肩／髋允许配置多轴，肘／膝为有范围的屈伸关节，不建模手指。关节参数与范围必须写入 `body_profile`，不在不同姿态间偷偷改变骨长。每个声明的接触状态同步求解全部已接触肢体，不能用四条独立距离判断拼成“人体姿态”。

A／B 的骨长建议沿用[场景与动作卡](05-scenario-and-movement-cards.md)。P0 默认接触末端取腕／踝，独立端点偏移为零，肘膝屈曲范围为 0–140°。肩髋轴、参考零位与宽松的合成限位仍属实施参数未决项：在交付计划 T01／T04 的骨架与首个正向运动学单例构造中记录并冻结，完成前不得开始对照实验。这些是算法试验边界，不是人体适用范围。

拟用 SciPy 有界最小二乘、多初值搜索接触残差。根位姿搜索范围、初值、最大迭代、重启次数与容差都进入配置；接触位置容差暂拟 0.015 m，作为工程假设记录。求解后重新做正向运动学，复核实际骨长、接触残差与关节范围；数值求解器的 success 标志不能独立决定通过。

输出根位姿、关节参数、派生关节点及残差。查看器仅把这些求解状态画成简化骨架；未找到解不补造姿态。P0 逐状态切换，不用插值动画暗示中间动作已求解。保持前一姿态作为初值也不能证明动态转换可行。

## 4. 检查与结果语义

P0 必做：schema 与引用、请求符合性、库存唯一性、布局锁定、装点边界、岩点之间保守包围体冲突、各接触姿态 IK 与关节范围。装点边界检查整个安装投影包围区域，不能只看中心；保守有向包围盒（OBB）由同一几何参数生成，并随安装旋转。包围体相交只表示违反本轮保守规则，不能证明真实岩点必然相撞。

几何数值容差默认 `epsilon_geometry_m=0.000001`，作为合成工程配置冻结。两包围体相交、刚好接触或最小间距不大于该容差均算冲突；大于该值才通过。边界比较仅允许此量级的数值误差，0.2 m 边距不因此改变。报告记录包围体、变换、间距或交叠依据及容差；距离计算失败为 unknown，不当作分离。

双手同时接触时先检查必要的距离上界。对固定目标点，令 `d` 为两目标的世界距离，`B=肩宽＋左右上臂与前臂长度之和＋左右端点偏移模长之和＋2×接触容差`。若 `d>B+epsilon_geometry_m`，可直接判该必要约束 fail，并保存 d、各项参数、B、状态 ID 和输入指纹；不依赖 IK 是否收敛。若以后允许在接触区域内自由选点，须改用两区域距离的保守下界，不能直接用中心距。`d≤B` 只通过此上界检查，仍须 IK；未知 IK 不升级为不可达证明。此契约对应[实验与验收](03-experiment-and-acceptance.md) AC06，结论仅针对声明的人体模型与接触误差。

每项输出 `status / reason_code / evidence / scope`：

- `pass`：该项在声明假设和容差内通过，保留数值证据。
- `fail`：可确定的数据或已检查约束违反，例如重复占用库存、安装区域越界。
- `unknown`：已尝试但无法判断，包括 IK 未找到合格解、数值失败或耗尽预算；不能写成 `impossible`。
- `not_checked`：该项未实现或不在本轮范围。

按数据、安装几何、姿态求解顺序执行。若上游输入无效，依赖它的检查标为 not_checked 并注明阻断项；不伪造后续失败，也不丢弃这个候选记录。前端展开后应能看到哪一条约束、哪个岩点或哪个状态产生结果。

P0 的受力／摩擦／平衡、抓握方向与力量、完整人体碰撞、连续动作转换均为 `not_checked`，留至 P1；真实难度、趣味及真人可攀性亦未验证。汇总只呈现各层状态和待处理项，不输出“可爬／安全”、V 等级或未经标定的总体成功率。侧拉方向可显示和解释，但不能因姿态 IK 通过就宣布侧拉成立。

## 5. CLI、结果包与协作边界

以下接口为拟议契约，尚无命令实现：

```text
python -m boulderlab validate --request request.json
python -m boulderlab propose --request request.json --out candidates.json
python -m boulderlab evaluate --request request.json --candidates candidates.json --out runs/<run_id>
python -m boulderlab bundle --run runs/<run_id> --out bundle.json
```

`propose` 先提供带种子的模板基线；Codex 提出的候选使用相同 schema，直接进入同一校验与评估流程。预算记录全部提出、淘汰及修改次数。命令退出码拟为 0＝流程完成、2＝输入无效、3＝运行错误；评估含 fail／unknown 仍可正常完成，以结果内容判断，不能把退出码当质量分数。

拟议工程目录：`fixtures/` 存场景、人体与案例；`requests/` 存请求修订；`runs/<run_id>/` 存输入快照、manifest、候选、评估与诊断；`reviews/` 存用户反馈。每次运行创建新目录，不覆盖旧证据。最终单个 `bundle.json` 嵌入所需快照、程序几何参数、求解状态与摘要，前端通过文件导入直接比较同条件结果；不读取任意本机路径或执行包内脚本。

用户在查看器中选方案、切状态、标注意见并导出 `review.json`，再把文件或意见交回当前 Codex 对话。浏览器不会自动唤起 Codex，也不静默修改源数据。

前端意见属于观察和偏好，例如“该脚步不符合意图”，不会覆盖 IK 或几何检查。由 Codex 据此提出新候选，再跑完整依赖链。比较页面同时保留被选中的方案和候选总数；求解耗时、检查次数及人工修订分别记录，便于后续比较模板与模型建议的实际成本。

## 6. 版本、失效与实施检查

评估指纹覆盖场景、库存属性、布局、动作方案、人体、评价配置、几何／求解器版本；使用规范 JSON 的 SHA-256。对象键排序，按 ID 存储的无序集合排序，动作序列保留顺序；拒绝 NaN 等非有限值。显示配色、备注不进入计算指纹。

修改任何计算依赖后，旧结果保留为历史；相对新输入标记 `stale`，不能沿用通过标志。`current/stale` 属于引用有效性，与四类检查状态分开。包中保存依赖版本、代码修订／内容指纹、种子与完整配置；相同种子不承诺跨数值库版本逐位一致。未知 schema 主版本拒绝导入，不静默猜测迁移。

进入实现后至少验证：坐标与倾角方向一致；固定模式拒绝改点；库存和边界错误可定位；包围体与显示使用同一变换；IK 成功状态可由正向运动学复核；未找到解为 unknown；P1 项始终显示 not_checked；输入变化使引用失效；导出再导入保留反馈所指向的候选版本。这些是待实现的验收要求，本轮仅交付方案。
