# Implementation contract · 2026-10-14

Local-only functional prototype with browser generation/check/view/edit, mixed-phase route search, finite inventory and one-level volume mounting. A localhost Python HTTP bridge (stdlib, no hosted API or model API) connects the browser to the same evaluator as the CLI and bundle workflow. This is the current contract; original MVP scope and historical acceptance remain in `outputs/mvp-preparation/`, `outputs/mvp-implementation/` and `tests/RESULTS.md`.

## Shared wire shape

- `request`: `{schema_version:"1.0",id,revision,source:"synthetic_assumption",profile?:"basic"|"competition"|"catalog"|"style"|"route",scene:{width,height,angle_deg,margin:0.2,inventory:[...] ,catalog_stock?:[...]},body:{id:"A",...parameters},scenario,mode:"free"|"fixed",hand_moves:2|3|4|8|10|12,seed,budget,solver:{...},reference_layout:[...],start_contacts:{...},end_contacts:{...},design_brief?:{...}}`. `basic` and `catalog` use a 3 × 3 m wall and `foot_first` / `sidepull` / `foot_reposition`; `competition` uses a 4.8 × 4.2 m wall, `competition_sequence` and exactly four hand transfers. Backend defaults are authoritative. Wall coordinates are metres: `u` right, `v` up from the wall base centre; positive angle is overhang. The Python API still defaults to `basic` for compatibility; the webpage opens the saved `route` comparison. The style profile uses a shared 23-hold 3 × 3 m wall, `style_search`, fixed layout, four hand transfers and 0–40° overhang. The `route` profile uses `route_search`, 8/10/12 hand transfers (default 10), `mode="free"` for subsequent edits and 0–40° input. Its shared `reference_layout` is a pool of possible installations, not an already installed wall; candidates contain only actually used placements. The older basic/competition/catalogue profiles retain the 0–10° limit.
- `candidate`: `{id,name,revision,parent_id:null|string,generator:"rules"|"codex"|"manual",placements:[{id,inventory_id,u,v,rotation_deg,contact_surface_id?:string,mount?:{parent_id,face_id}}],states:[{id,label,contacts:{LH:contact|null,RH:contact|null,LF:contact|null,RF:contact|null}}],events:[{limb,from_state,release_state,to_state}],design_notes:[string]}`. Each contact is `{placement_id,contact_id:"main"}`. `main` aliases the placement's selected surface for the whole sequence, or the legacy hold contact when no surface is selected. One limb event has release and touch states; initial contacts are not hand moves.
- `evaluation`: `{id,candidate_id,fingerprint,version,checks:[{id,status:"pass"|"fail"|"unknown"|"not_checked",label,detail,state_id?:string,placement_ids?:string[],evidence?:object}],poses:[{state_id,status,joints:{pelvis,neck,left_shoulder,right_shoulder,left_elbow,right_elbow,left_wrist,right_wrist,left_hip,right_hip,left_knee,right_knee,left_ankle,right_ankle},residual_m,...}],summary:{status,passed,total},elapsed_ms}`. joints are world xyz arrays; failed/unknown poses do not invent joints. P1 entries not_checked excluded from P0 pass total. Root frontend stale is separate from check status.
- `bundle`: `{schema_version:"1.0",id,created_at,request,candidates:[...],evaluations:[...],manifest:{...},reviews?:[...]}`. Immutable snapshot.

## Standard catalogue and installation geometry

- `catalog_metadata()` returns nine records with `{id:type,template_id,template_name,type,width,height,depth,default_count,min_count:0,max_count:20,grip_surfaces,mounting_faces?,taxonomy}`. `catalog_counts` is keyed by type. Defaults are `jug:6`, `directional_edge:4`, `crimp:6`, `pocket:2`, `foothold:8`, `sloper:2`, `pinch:2`, `rail:2`, `volume:2`: 34 actual inventory instances, not 34 automatically installed objects. Counts must be integers from 0 to 20. Missing required stock is an error; no instance may be installed twice.
- Inventory holds have `{id,type,width,height,depth,template_id?,template_name?,contact:{id:"main",position:[x,y,z],radius,limbs},grip_surfaces?,mounting_faces?,taxonomy?}`. Catalogue instances share their standard template's exact geometry and surface definitions. `scene.catalog_stock` records each template once as `{template_id,template_name,type,count}` and must match inventory counts. `fixtures/catalog-templates.json` is the exported standard metadata.
- `taxonomy:{family,preferred_role,roles,form,legacy_alias?}` separates shape family, potential use and form. Canonical families in this prototype are `jug`, `crimp`, `pinch`, `sloper`, `pocket`, `foot_chip`, `volume`; they are not an exhaustive industry ontology. Legacy `type="directional_edge"` maps to crimp/edge and `type="rail"` to crimp/rail. Family and potential roles never override the selected surface's `limbs`. Sidepull/undercling describe use direction rather than a new shape family. Crimp uses a thin edge region; Pocket separates its recessed hand contact from its external standing surface. Their original parameter geometry is shared by thumbnail, inspector and wall display.
- A grip surface is `{id,label,position:[x,y,z],normal:[x,y,z],u_axis:[x,y,z],v_axis:[x,y,z],radii:[u,v],limbs,pull_direction:[x,y,z]}` in the hold's local coordinates. Typical IDs are `working` and `alternate`; volumes expose `face_1_grip` through `face_3_grip`. The region is a declared contact hypothesis. IK uses one representative point, not an arbitrary point search or multiple simultaneous points. Normal and pull direction are geometry/design declarations, not solved contact forces or friction evidence.
- A mounting face is `{id,label,origin:[x,y,z],u_axis:[x,y,z],v_axis:[x,y,z],normal:[x,y,z],polygon:[[u,v],...]}`. Frames must be right-handed and orthonormal. The three faces correspond exactly to the displayed triangular pyramid: apex `(0,0,depth)`, rim `(-.49w,-.45h)`, `(.49w,-.32h)`, `(-.23w,.49h)`, skirt `min(.008,depth*.06)`. A face origin is its triangle centroid.
- Only one layer of `volume → non-volume` mounting is allowed. A mounted child's `u/v` are metres in the selected parent face; rotation is around that face's normal. Missing parents/faces, cycles, nested mounts and hidden normal offsets are invalid. The child's complete rectangular base must lie inside the face polygon. Parent transforms, child rotation and wall angle all affect rendered geometry, contact targets and fingerprints.
- `boulderlab/geometry.py` owns contact transforms, mounting frames and conservative 3-D OBB geometry; `boulderlab/catalog.py` owns standard stock. Collision uses 15-axis OBB SAT. Only a valid direct parent–child mounting pair is exempt from collision; sibling children and all unrelated objects remain checked. The entire transformed bounding box is checked against wall margins. Full human collision remains unimplemented.
- Free-mode edits create new candidate revisions. Installing consumes an existing available inventory instance; uninstalling returns that same instance. The UI blocks uninstalling an item referenced by the contact sequence or a parent still carrying children. Installing spare inventory does not silently add it to the sequence. Fixed mode locks coordinates, rotation, surface selection, installation and removal.
- The default catalogue route uses a foot contact on `foothold_03`, mounted on `volume_01/face_1`; unused `directional_edge_03` is mounted on `face_2` when stock permits. Competition remains a synthetic design study, not a competition replica or fixed-board multi-route search.

## Algorithm scope — user clarification, 2026-10-14

Training boards are references for route construction and evaluation logic. Their visual appearance and hold layouts are secondary. Preserve the v0.2 distinction between selected holds/roles, possible hand-foot sequences, and a separately evaluated layout. Official setting workflows, public third-party generation algorithms, and our own hypotheses must be attributed separately; no claim of access to proprietary board algorithms.

The retained `style` baseline performs bounded contact search; the three older profiles retain their scripted baselines for regression and installation studies. It freezes synthetic placements and searches hand and foot choices/order within a deliberately narrow grammar: exactly four hand transfers, one preceding foot transfer per hand, each limb transferred twice, ascending contacts and declared finish contacts. It does not enumerate arbitrary moves, matching, skips, dynamic trajectories, or endurance-length routes.

### Retained four-transfer style search contract

- `request.route_design`: `{style_goal,rhythm,source:"synthetic_assumption",search:{beam_width:128,max_expansions:16000},phases:[{id,label,hand_move_index,target:{strength,power,technical,load}}]}`. Four ordered phases cover the four hand transfers. Defaults in `boulderlab/route_design.py` are the authoritative coefficients. Body, geometry, start and finish remain identical across default style comparisons.
- Each hold may have `design_attributes:{source:"synthetic_assumption",grip_accessibility,precision,force_demand,friction_dependence}`. These are declared affordance priors on 0–1 scales, not difficulty grades. They are original engineering assumptions, not manufacturer measurements. `friction_dependence` is currently descriptive and does not implement a friction calculation.
- Per-move estimates use selected contact coordinates and transformed declared pull direction, displacement/arm length, wall inclination, support-foot accessibility/precision, supporting-hand demand and lateral offset. They expose four 0–100 indices: `strength` (grip/support demand proxy), `power` (span/orientation proxy for explosive tendency), `technical` (precision/direction/support proxy), and `load` (weighted movement demand). No solved forces, watts, energy units or cognitive ability are implied.
- A sequential burden state uses `next = previous × (0.72 + 0.22 × load/100) + load`; contextual demand is `load + 0.12 × previous`. This state can exceed 100. These coefficients are uncalibrated, not a physiological fatigue/recovery model. The phase load objective is capped at 100; the per-move raw load and contextual burden remain separately available.
- Beam search ranks partial sequences against each stage's target, using style-specific weights. It preserves multiple contact states, then selects distinct hand sequences before feet-only variants. State deduplication may merge different prior-load histories, so the beam is not an exhaustive or globally optimal solver. The seed is recorded for IK; style search ordering is deterministic and does not randomize when the seed changes. Its broad contact-distance bounds are necessary-condition filters only. Every returned candidate independently goes through unchanged P0 geometry and IK checks; candidates are not relabelled after checking.
- `candidate.search_metadata` records algorithm/version, expansion limit/count, beam width, complete sequences encountered, returned count, distinct hand sequences, pruning counts and budget exhaustion. Counts describe this bounded search, not all possible routes. No solution under this grammar/budget is not proof that the wall is unclimbable.
- `evaluation.design_analysis` is recomputed from the evaluated request and candidate. It includes per-move attributes and demand indices, phases with intended targets and computed estimates, average dimensions, peak strength/power, mean technical demand, summed load, contextual peak and its event, objective cost, search metadata and explicit limitations. Targets and scores are distinct; a late-crux goal can still produce an earlier estimated peak. `dimensions.load` is the raw hand-move mean, while `phases[].estimate.load` is the contextual capped demand actually used by the objective.
- Changing style or phase targets for the same candidate may change objective cost but cannot change its underlying move-demand estimates. Candidate edits invalidate the whole report. Imported analyses are recomputed for consistency, even when a modified bundle has a newly signed outer digest. Backend code provenance includes the new module. Generation statistics are reproduced by cheap search and matched against the current geometry/sequence; a manual revision that no longer matches does not inherit trusted statistics from its parent.
- `GET /api/style-examples` returns `{examples:[{id,label,bundle}]}` for three independently validated saved bundles. `POST /api/style-comparison` accepts shared `{body_id?,angle_deg?,seed?,budget?,rhythm?}` and generates the same envelope. All three requests share settings and default to `late_crux`; unlike requests are never merged into one bundle.

The `route` extension below implements mixed stage targets and longer bounded sequences. Arbitrary phase plans, unrestricted alternative beta, full endurance-route modelling and trial feedback remain further work. Difficulty/quality prediction requires separate data and calibration; neither objective fit nor discrete IK establishes continuous transition feasibility or real climbing difficulty. Outdoor reading contributes feature discovery and phase-connection ideas without expanding this indoor prototype into outdoor installation or protection planning.


## Complete route search and history model

`profile="route"`, `scenario="route_search"`, `hand_moves ∈ {8,10,12}`. `route_program` selects `mixed_flow`, `power_finish` or `sustained_finish`; all three share the synthetic inventory and possible installation pool, start contacts and same TOP target. The planned sequence orders establish, technical, power, relief and sustained stages before a separate final TOP-matching stage. The last two hand transfers belong to `phase_kind="finish"`, rather than being labelled a power or sustained crux merely because of the program name. A label is a desired stage, not evidence that its intended crux or recovery occurred.

The request extends `route_design` with `program`. Its `phases` still contain one entry per hand transfer, with unique `id`, `hand_move_index`, `segment_id`, `phase_kind`, `label` and four-dimensional `target`; consecutive entries sharing `segment_id` form one displayed phase. The analysis groups them into actual `event_start/end` and `hand_move_start/end` ranges, with targets, estimates and entry/exit accumulated state. The UI never assumes four stages or eight events.

The bounded search chooses targets from the possible installation pool and allows 0–2 foot adjustments before a hand transfer, with both hands eventually matching TOP. It tracks prior relative load and installed inventory while ranking stage fit. Returned candidate placements contain only instances referenced by the chosen contact sequence, rather than the entire pool. This is discrete selection among predetermined candidate positions, not unconstrained spatial optimization. Search limits, contact grammar and rough geometry tests can reject or miss routes; they do not establish that the actual wall is unclimbable. Every returned candidate still undergoes independent P0 checks. Model targets never relax collision or IK checks.

`boulderlab/full_route.py` is authoritative for coefficients. Let `L` be the previous accumulated state and `d` the raw single-action load. Let `a` and `g` be the current hands' mean grip accessibility and force-demand priors, `f` the foot-support metric and `i` the inclination metric. The current uncalibrated history update is:

```text
rest_opportunity = max(0, (a − 0.65) / 0.35) × f × (1 − i) × max(0, 1 − g)
recovery_proxy   = L × 0.24 × rest_opportunity
next_load        = max(0, 0.91 × L + 0.70 × d − recovery_proxy)
effective_burden = d + 0.17 × L
fresh_burden     = d
```

Phase labels and targets do not enter the rest calculation. A relief target may still accumulate load when incoming effort and the selected contacts provide insufficient relief. These quantities have no physiological units, may exceed 100 and do not measure remaining energy, muscle fatigue, recovery time or injury risk. The four per-action demand indices still describe synthetic strength, explosive tendency, technique and raw load; they are not components of a calibrated V-grade predictor.

Each analyzed move exposes `prior_load`, `rest_opportunity`, `recovery_proxy`, `fresh_burden`, `effective_burden`, `accumulated_load` plus the existing geometric attributes and four dimensions. `history_comparison` includes hand-move `fresh_peak`, `with_history_peak`, their `delta`, `late_move_delta` (mean history increment over the last third of hand transfers), `initial_load`, `source` and a description. This compares the same selected action sequence with zero prior state at every action against continuous propagation; it does not generate a second route or represent a human experiment. Underlying demand/history estimates depend on the candidate and context, not its requested program label; targets affect objective cost and choice.

`GET /api/route-examples` returns `{examples:[{id,label,bundle}]}` for the independently validated saved programs. `POST /api/route-comparison` accepts shared `{body_id?,angle_deg?,hand_moves?,seed?,budget?}` and returns that envelope after generating all programs. Shared conditions are held constant, while each program retains its own request and analysis; distinct requests are never merged into one bundle. `POST /api/request` accepts `route_program` for individual generation. Edits invalidate the report and provenance is rechecked when exported/imported, as with the retained style baseline.

## Independent beta audit on installed geometry

`POST /api/beta-audit` accepts exactly `{request,candidate}` for `profile=route` or `profile=setting` and returns `beta-audit/1`, separately from generation bundles. The original request/candidate are unchanged. Search reads installed placements and selected-surface limb permissions only; it never installs unused inventory, consumes planned phases, imposes the original hand count, or rewards coverage. Both objectives have bounded beam/expansion/depth budgets under a shared 45-second deadline, including original and alternative IK evaluation. Exhaustion and unverified sequences remain visible; no search result proves uniqueness, optimality, or real climbability. Unmodeled same-contact release/regrabs are rejected so they cannot inflate reported savings.

Candidates retain every original placement and only replace contact states/events. The independent evaluator relaxes the requested hand count for route audits; the normal schema, geometry, selected-surface permissions, start/TOP constraints, release chain and actual IK checks remain. Independent evaluations carry `sequence_policy=independent_beta` and cannot be imported as ordinary generation evidence. The report stores original fingerprint, geometry hash, engine hash and audit code hash. GUI edits, candidate changes and rechecks invalidate its view. Audit JSON downloads separately; original generation exports retain their original candidate/evaluation contracts.

Audit search permits arbitrary single-limb order, hand matching, reusing earlier holds and bounded backtracking; it removes the generator's hand-above-foot and narrow stance filters. Both feet cannot occupy the same representative point, and each installed hold still exposes just one selected representative point. No heel/toe hook, smear, detached feet, simultaneous release or continuous dynamics are implemented. Coarse necessary span filters precede independent IK; incomplete solutions have no displayed skeleton.

`analyze_beta` recomputes each alternative's load history without phase names. Total proxy effort sums historical burden plus nominal retained-hand pull/foot-support geometry penalties. The nominal trunk is a geometric estimate, not a solved centre of mass; no force, friction, torque or physical stability conclusion follows. Peak historical burden is a separate metric with a different calculation basis from total proxy effort. Crux reporting distinguishes contact with the original hold, hand contact, reuse of the same limb/source/destination transfer, and whole-route peak change. It does not equate touching the same hold with preserving the same difficulty.

Current evidence is saved under `outputs/beta-audit-study/`. Earlier 201-test/full-route records above describe the previous baseline; this audit's test and browser results are recorded independently.

### Shared-contact capacity and direct skip challenges

Browser inspection exposed a false shortcut that matched both hands on a tiny Pocket patch. This is retained only as a historical model counterexample under `outputs/beta-audit-study/history-unrestricted-matching/`; none of those routes is current accepted evidence. Audit model v2 applies a conservative synthetic matching policy: only Jug/Sloper/Rail of at least 0.24 m width and 0.10 m height, with selected patch major/minor diameters at least 0.08/0.03 m, may match hands. Pocket/Crimp and smaller surfaces cannot match. Simultaneous hand/foot or two-foot occupancy of one representative point is rejected; sequential reuse remains possible. These are search assumptions, not a measurement of human hand capacity or proof of contact feasibility; even accepted large holds lack separate hand-surface contacts.

When neither independent beam objective returns a verified alternative, a bounded direct skip challenge supplements it: remove the original model-crux transfer first, then an early removable transfer, rebuild the whole contact chain and recheck with the same IK and shared deadline. At most two such candidates are checked. The original beam's unknowns remain in the report. `search_source` distinguishes this local counterexample search from independent beam search, and the UI explains that provenance. Finding one verified skip disproves necessity of that prescribed contact within this model; it does not establish the best whole-route beta.


## Geometry and beta co-design

`profile=setting`, `scenario=setting_search` uses three authored spatial seeds (`diagonal_balance`, `opposing_sidepulls`, `roof_exit`) and independently searches single-limb contact transitions. It does not consume the route profile's phase plan or exact hand-count requirement. The legacy `hand_moves` field is retained for schema compatibility, not enforced for this profile. Start contacts, matched TOP, contact permissions, release chains, inventory, installation and discrete IK remain checked. Installed but unused points are allowed.

The bounded loop searches the seed, proposes coupled hand-position / direction / supporting-foot changes from its actual beta, then searches each proposed geometry anew. The current diagnostic study selects P0-verified betas by release-state equilibrium fraction, then all-state equilibrium fraction, then finite required capacity utilization. Lateral travel, directional demand and foot/hand transfer ratio remain descriptive geometry indices, not human movement quality, a calibrated grade, or a proof of difficulty. A proposal can fail or remain unknown; the unchanged seed can legitimately win. Every displayed alternative has its own checked contact sequence on the selected geometry. Baseline and alternative evidence is nested under `candidate.setting_report`, bound to the same request and validated on bundle import. Editing creates a new revision and removes the old setting report.

`GET /api/setting-examples` returns three separately validated `{id,label,bundle}` examples. `POST /api/setting-comparison` accepts only `{body_id?,seed?,budget?}`; custom wall-angle or exact-hand-count controls are not silently accepted by this comparison endpoint. The normal request endpoint accepts `setting_program`. The UI displays actual before/after geometry, independently found sequences, accumulated model burden and finite search evidence.

### Structural wall panels

Optional `scene.wall_panels` entries have `{id,label,origin:[u,v,z],rotation_deg:[rx,ry,rz],width,height}`. Their origin is the panel's bottom centre in the base-wall coordinate frame; their axes are `wall_basis(scene.angle_deg) @ Rz(rz) @ Ry(ry) @ Rx(rx)`. Root placements use panel-local `u` and `v` and declare `wall_panel_id`; absent/unknown panel references are errors when panels exist. Root hold rotation occurs about that panel's normal. Mounted children inherit the parent's complete frame and must not also declare a panel.

Checks use each panel's rectangle and existing edge margin for root footprints, parent face polygons for mounted children, and world-space OBBs for hold collisions. Contact search uses transformed positions and global-wall projections for progress, rather than comparing unrelated local panel coordinates. Local inclination influences the synthetic demand model. Rendering and editing use the same frames. Legacy requests without panels retain the original single-plane behaviour.

Panels model planar facets, including an actual connected 18° lower overhang / 4° upper exit in the example. They do not model continuous curvature, whole-body collision with the wall, a structural wall design, or landing-zone clearance. Smearing, heel/toe hooks, momentum and simultaneous dynamic releases remain unsupported. The quasi-static diagnostic below adds declared contact-force and friction assumptions, not measured real-world contact properties. Technique names are extensible descriptive vocabulary, not a claim that those techniques have been simulated.


### Professional workflow and height terminology

The interface exposes an educational seven-step workflow referenced to CWA PRS training: brief, spatial/inventory constraints, movement/layout co-design, computational checks, human forerunning, another setter's review, and iteration/feedback. Human stages remain unverified; existing design feedback is not reclassified as a forerun record or certification.

Display height distinguishes nominal unfolded layout height from the actual maximum front-panel world-y coordinate relative to model ground (y=0). This geometric readout is not EN 12572-2:2017 wall height: §3.6 measures from the top of the impact area to the highest possible holding point; §4.1 limits this to 4.5 m, or 4.0 m when standing on top is possible. The model does not establish either the true impact-area surface or all holdable wall edges. Walltopia's 3 m planning minimum is manufacturer advice, not a universal standard minimum. No automatic compliance result is generated.

## Product boundary: routesetter drafts, not a human simulator (2026-10-14)

The user's intended product generates editable first drafts and movement inspiration. A routesetter reviews and modifies them, then installs and foreruns them on the actual wall. Computational results assist that decision; they do not authorize opening a climb or replace forerunning. Completing a detailed simulation of skin, muscles and dynamic movement is not a prerequisite for this product.

Rules must identify their evidential layer:

| Layer | Required accuracy and use | Current limitation |
| --- | --- | --- |
| Space / inventory / installation | Preserve metric dimensions, frames, quantity, selected contact and mounting relationships; reject malformed data | Panel footprints and OBBs are approximations, not structural or physical installation certification |
| Reach / pose | Explain reach constraints and provide a reproducible pose when solved | Synthetic segment lengths and joint limits; IK non-convergence is unknown, not proof of impossible climbing |
| Contact / static support | Flag weak support or incompatible orientation under declared assumptions | A single COM/pose, conservative friction cones and synthetic per-limb grasp envelopes; static failure does not reject dynamic beta |
| Movement / search | Offer alternative sequences and disclose the searched action space | Corridor pruning, matching policy, beam width and time limits may exclude valid human beta |
| Style / rhythm / difficulty | Explain experience-based features and provide contrasting drafts | Hand-family capacities and burden/history coefficients are uncalibrated; no human grade, true energy or fatigue prediction |
| Setter / forerun feedback | Preserve suggested changes and eventually record on-wall outcomes separately | Current comments are design feedback; there is no calibrated learning from real foreruns yet |

The three current setting studies use static-support-oriented selection among P0-verified candidates. This is a diagnostic experiment, not a universal routesetting quality function. In particular, do not optimize every route to maximize static feasibility or discard dynamic style for failing this test. Meaningful product acceptance is setter usefulness, editable and installable proposals, variety, understandable problems, and later observed revision/forerun outcomes. Do not invent numerical success targets without pilot data.

### Quasi-static diagnostic implementation

`boulderlab/statics.py` evaluates every solved contact/release pose using a declared synthetic segment COM, gravity, force and moment balance. Feet and slopers use unilateral Coulomb friction; other supported hand types use explicitly synthetic aggregate grasp envelopes, not tensile forces derived from a heightfield normal. Eight inner cone rays and per-limb axial force capacities form a linear program minimizing required common capacity utilization. Force/torque and original circular cone residuals are rechecked. Unknown geometry, poses or parameters remain unknown. The result is `Evaluation.mechanics_report`, separate from P0 and from unverified real human capabilities. Model parameters and source code enter provenance, and imported reports are recomputed rather than trusted.

Template foothold working contacts now sample the actual upper ledge; renderer and solver share that surface. The existing three seed layouts are reevaluated and proposals adjust hand orientation and support-foot positions using failed/loaded release poses, followed by independent beta search and new IK/static checks. A failed proposal is retained as evidence and need not replace the baseline.

### Scanned geometry entry and its boundary

`web/src/scan-geometry.ts` and `scan-model.ts` provide local STL/OBJ parsing (15 MB, 150,000 triangles), explicit metre/centimetre/millimetre and Y/Z-up conversion, preserved scan origin, mesh inspection and a selected triangle's centroid/right-handed frame. Export includes original and normalized geometry hashes, exact metre vertices, triangle/barycentric annotation and manual normal-flip provenance. Surface roughness for rendering is never interpreted as a friction coefficient. An original full 3-D undercut and an irregular faceted wall are demonstration assets, not claimed real scans.

This workbench does not yet replace route-solver geometry, collision proxies or mounting faces. Imported mesh contact mode, friction and force capacity remain unassigned; a selected triangle is only a geometric annotation. The next useful integration needs a real sample, known dimensions/registration and human-marked contact/installation regions. It does not require modelling every grain of surface texture. Fine contact and whole-body dynamic simulation are intentionally outside the current product scope.

### First-principles rule audit

Search and evaluation now share `kinematics.contact_distance_bound`: actual rigid torso anchor separation plus limb segments, both endpoint offsets and contact tolerances. This replaces inconsistent reach cutoffs and an arbitrary cross-limb allowance. Passing this necessary bound still does not establish a solvable posture.

Search corridors and matching policies remain declared search restrictions, not physical impossibility tests. OBB overlap is a conservative proxy collision rather than exact mesh intersection. Each installed hold exposes only one chosen representative contact; hand-only template patches currently omit potentially valid feet on large jugs. These are representation limits. Shared two-hand patch capacity is not solved, and synthetic static capacities are not reduced by the separate history-load proxy. The model has no action durations and does not measure physical power, energy or fatigue.

## External mesh inventory and structural wall variants (2026-10-15)

`assets/holds/library.json` is a versioned local registry of four prepared SetRsoft meshes. The original GLB files, upstream README, hashes, source links, CC BY-SA 4.0 attribution and modification notices are retained under `assets/holds/`. Family classification and contact annotations are AI drafts; scale and installation are explicitly unverified. The current families are Jug, Crimp, Pinch and Sloper. Pocket remains an explicitly labeled parametric fallback because no suitable, obtainable and redistributable pocket mesh was secured. A bolt recess is not classified as a finger pocket.

Every registered mesh uses a right-handed local frame: XY footprint centered at the origin, back minimum z=0, positive z outward. Indexed triangles retain non-heightfield geometry; simplification does not fill holes or replace the mesh by a convex hull. Per-instance scaling is uniform and uses an unmeasured demonstration width. Two declared grip regions per mesh include exact triangle/barycentric anchors, outward triangle normals, orthonormal tangent frames, annotation triangle IDs, elliptical extents, limb permissions and suggested pull directions. These are separate from friction and force assumptions. Pinch sides are recorded as a pair, but the solver still uses one selected aggregate grasp envelope.

Inventory references bind `asset_id`, geometry and record SHA-256 values, `asset_scale` and `asset_source=external_mesh`. Validation reconstructs dimensions and contacts from the current registry, checks mesh bounds and source metadata, rejects changed anchors/normals, and refuses partial or stripped references when mesh markers remain. Frontend failure omits the unavailable asset rather than silently rendering a template with unrelated contacts. Scene, near view and thumbnails use the same indexed mesh, and patch overlays remain on declared triangles. Collision remains conservative OBB; the installation backplate is not a volume face for mounting children.

`hold_source=auto|assets|templates` selects the setting inventory. Auto uses an available valid registry; explicit assets requires usable assets. Missing families may retain an explicit `asset_fallback_reason`; a malformed registry is an error. Asset substitution preserves the existing XY contact corridor by shifting the installation origin, while depth and normals follow the actual mesh. A bounded 5 mm-axis search moves nonanchor feet up to 7 cm to separate conflicting OBBs and records all changes. Existing search, posture and static thresholds remain unchanged. The saved template and asset groups use shared spatial briefs but also differ in family substitutions and installation repairs; they are not a controlled experiment in geometry fidelity alone.

`wall_profile=default|overhang|roof|dihedral|arete` is supported for setting requests. Default preserves the three original example structures. Overhang is a 25° panel. Roof joins a 2.1 m vertical panel, 0.8 m horizontal underside and 1.3 m exit panel along exact shared edges. The two corner options join panels rotated ±35° around the vertical axis, reversing the normal directions for an inside corner versus an outside edge. All are demonstration structures; `scene.angle_deg` rotates the complete construction. Installation, contact targets, direction arrows, search and checks inherit actual panel transforms.

Nondefault wall adaptation folds the original seed's developed coordinates onto panels, fits the entire hold footprint inside the existing margin and records changes. A separate bounded spacing repair can move nonstart placements by at most 25 cm in 5 mm increments on their assigned panel; it does not reduce hold sizes or relax collision rules. Panels are structural surfaces, not movable volumes. Wall thickness is illustrative; complete wall/body collision and structural safety remain unverified.

If the existing search finds no complete beta on a nondefault wall, the result may contain `layout_report.status=no_sequence`, one actual start state and zero events. It is an inspectable layout draft. It has no setting improvement report or movement-load analysis, and normal P0 evaluation still fails request conformance because TOP was not reached. No complete route or pose sequence is fabricated. Current projected-height and corridor pruning can exclude legitimate roof/corner moves; this result is not a proof of human impossibility.

`GET /api/setting-examples?hold_source=assets|templates` reads the two saved three-route groups. `GET /api/wall-examples` reads four separately validated wall drafts; optional `wall_profile` selects one. Setting comparison and request POST endpoints accept hold and wall sources. Three selectable scene palettes affect only rendering and local preference, never the request, geometry, evaluation or bundle fingerprint. Same-route hand/foot holds share color; selection/contact indicators and unused-hold contrast remain separate.

Reproduction: `scripts/prepare_demo.py` generates all 24 current example bundles; `--profile setting` generates the two three-route groups and the default alias, `--profile wall` generates four wall examples. `scripts/report_asset_study.py` validates current bundles before recording comparison data. Final checks and browser evidence are stored in `outputs/asset-study/verification.json`; old outputs remain historical evidence, not current checks.
